# ChunkseeKit — Repository Instructions

Read with the shared `AGENTS.md`. Project record: fahlman/ChunkseeKit#1.

## Read, interpret, display

Ryan's rules, approved 2026-10-25:

- The code knows formats, not content. What exists (blocks, items, mobs, biomes, structures,
  versions) comes at runtime from the save, the installed Minecraft, the world's data packs
  and the language files.
- **WWMD — What Would Minecraft Do?** Do what Minecraft does, unless Ryan explicitly
  chooses otherwise.
- **Lists are for exceptions,** and exceptions are facts in the game's code that the data
  doesn't tell us. Each entry names its code source. Anything the data could supply is a defect.
- Code-only facts are regenerated by a tool at each release. They are never hand-typed and
  never kept per snapshot.
- **Show what we can.** Never hide saved data because it's unfamiliar. "Unknown" is only for
  the facts the data can't tell us.
- **No version numbers in code or UI text.** Data readers read any version whose files parse.
- **Be useful, not a pain.** Notices inform and never block.
- **No self-made maintenance.** A new Minecraft version should need no code change, or at
  most one tool run.

Ryan's storage rule, approved 2026-11-15 (fahlman/Chunksee#581): the app and Kit write
property lists for their own persistence and cache identities, never JSON. Existing JSON stores
start fresh; do not add conversions. External Minecraft and service JSON remains readable.
AssetJSON's transient decoder normalization and legacyTextData's reproduction of Minecraft's
historical sign/book spelling belong to that external-input exception, not storage or keys.
Agent check scripts and evidence are outside this product rule.

ChunkseeKit owns reading and interpreting game data; ChunkseeIndex aggregates its typed
facts. Clients choose presentation, including language and deliberate fallback colors or
symbols. Establish format behavior from the game's own definitions and code.

Existing implementation notes below describe the current code and its evidence; they are not
exceptions to these rules. The remaining migration is recorded in
[fahlman/ChunkseeKit#222](https://github.com/fahlman/ChunkseeKit/issues/222):
data-reader version gates on #217/#218; shared tags and possible biomes on #233/#223;
enchantment definitions on #224; language files on #225; remaining copied data on #228/#232;
saved facts currently discarded on #229/#235; and source-generated code-only facts on #222.
The current mob reader already follows the saved format without a type catalog. Code-only
defaults still limited to verified versions remain unavailable elsewhere until the regeneration
work supplies evidence; a missing default must not suppress other readable facts. #227 records the reviewed block-item investigation and Ryan's subsequent decision to generate
actual default properties through the single release tool, without item-model substitution.

## Project

ChunkseeKit is the engine for reading Minecraft: Java Edition world saves. Ryan intends to
open-source it so others can build their own GUIs on it. The core library owns the file formats:
NBT, Anvil region files, chunk decoding, and the world-folder layout. The package's separate
ChunkseeIndex library owns aggregation over typed facts. Neither has UI or app code.
The Mac app **Chunksee** (`com.fahlsing.Chunksee`, fahlman/Chunksee) lives in its own
repository and depends on this package, the way Euchre depends on EuchreKit. Dependency direction:
**Chunksee app → ChunkseeKit**. Both were renamed from MCWorld and MCWorldKit on 2026-10-10
(fahlman/Chunksee#75).

- **Kind:** Swift package (a library plus a command-line tool). It is not a Mac app, so it has
  no `.xcodeproj`.
- **Products:**
  - `ChunkseeKit`, the library.
  - `ChunkseeIndex`, shared aggregation over the reader's typed facts. Its first API,
    `StoredItemTotal.totals(in:)`, owns per-ID quantities and outer-container counts, including
    nested contents. This product is available in v0.37.0; app adoption follows this release.
  - `ChunkseeKitTestSupport`, synthetic save builders for test targets, using the reader's public
    NBT and compression APIs. This additive product is introduced in v0.35.0; app adoption
    follows that release, tracked on #82.
  - `chunksee`, a command-line tool that inspects a world and decodes every chunk (`scan`). It
    uses only the library's public API and serves as a working example for GUI authors.
- **License:** MIT (`LICENSE`).
- **Dependencies:** Foundation, Apple's CryptoKit and system zlib through `CZlib`. There are no package
  dependencies, so there is no `Package.resolved` to track (it is git-ignored).

`ChunkseeIndex.BiomeArea.connected(in:)` owns edge-connected biome grouping, representative-member
selection and exposed chunk sides. It preserves every area and ignores unmappable chunk origins.
This pure aggregation takes chosen biome membership; file reads, surface/cave policy, display
names, colors and drawing paths stay outside it. Membership and boundary discovery share one walk.
This additive API is available in v0.42.0; app adoption is tracked on fahlman/Chunksee#383 and #214.
It changes no save reader, cache interpretation or held cave-biome rule.

`ChunkseeIndex.PointIndex` owns immutable region buckets and broad point-candidate lookup, using
the core checked coordinate conversion and region size. Results preserve input order and retain
unbucketable entries for the client's final checks; unusable bounds return the full snapshot.
Sparse queries inspect occupied buckets instead of enumerating huge empty ranges. This is the
app's existing PointMarkers lookup, with viewport conversion, precise geometry, visibility and
presentation kept outside the library. The additive API is available in v0.43.0; app adoption is
tracked on fahlman/Chunksee#384 and #214. It adds no reader, cache or task owner.

`ChunkseeIndex.SearchQuery` owns the app's existing category-prefix parsing and all-word matching.
Recognized prefixes ignore case and trim horizontal whitespace; unknown prefixes stay literal.
Its explicit phrase initializer preserves the CLI's contiguous, case-insensitive `find`/`text`
queries, including spaces and colons. Both forms share one substring matcher. The CLI consumes
that owner; app names, prompts, symbols, category membership and result formatting remain outside
the library. This additive API is available in v0.44.0 and adopted by fahlman/Chunksee#385.
Retained world-index state and typed result aggregation remain separate work on fahlman/Chunksee#214.

`ChunkseeIndex.NotableBlock` is a tag or direct-block identity, not a fixed ore enum.
Its Catalog consumes the composed `minecraft:ores` entries exposed by GameTag, retaining
immediate effective tag groups and direct members, including pack additions and replacements.
GameTag.entries reuses ResourceTagReader's existing composition, nesting, optional-reference,
cycle and budget rules; flattened members remain available to existing consumers. No second
resource reader or ore list is introduced. The explicit product exceptions remain Nether Gold,
ancient debris, spawners, trial spawners and budding amethyst. Nether Gold is excluded from
other groups. Empty tags remain distinct from unavailable definitions. Labels stay client-owned:
pack `tag.` names or GameNames readable IDs for tags, ordinary block names for direct members.

`Dimension.countBlocks(region:matching:)` owns the independent terrain-only pass. It uses the
existing normalized chunk/palette counter, skips partial-generation chunks, and does not read
entity/POI files, containers, biomes, structures or heightmaps. Missing terrain is empty;
damaged and unsupported individual chunks are skipped through the same visitor/terrain policy
as the core scan, preserving readable neighbors. File-opening errors and cancellation throw.
Requested-ID coverage describes the readable, supported chunks in that source file. Its
RegionBlockCounts property-list archive owns per-ID counts, section-height bounds, requested-ID
coverage and a separate interpretation (revision 1, depending on the whole terrain contract).
It declares no additional generated facts; those belong to the terrain dependency. Clients add
their existing terrain file-stamp primitive to cache identity, not a second staleness rule.
InterpretationSourceTests requires independently reviewed entries for both regionFacts and
blockCounts after every core-source change. InterpretationOutputTests also keeps a count archive
witness with readable, legacy, damaged and partial-generation neighbors.

`ChunkseeIndex.BlockCountIndex` retains raw counts independently of core RegionIndex and
DimensionIndex. Query-time catalogs regroup known IDs without file reads; requested new IDs
require coverage before completion. Unsearched, completed empty, failed and completed counts
remain distinct; failures/invalidation retain last good values without claiming fresh coverage.
Deletion removes contributions. Clients own file stamps, source/task lifetimes and scheduling.
BlockSearchOrigin owns finite X/Z distance and occupied-region ring ordering. nearestDeposits
ranks by chunk-center distance before the client limit, with chunk X/Z and group ID tie breaks.
matchingDeposits returns both that nearest list and the full matching chunk/group-row total
from one grouping pass. Nonpositive limits return only the total; nearestDeposits keeps its
existing empty-list behavior. Totals describe currently retained counts, including last-good
values after a failed refresh, not an estimate for unsearched regions.
Raw counts are shared; origin and grouping are query inputs, so windows order independently.
The app owns captured-player/fixed-map-center lifetime and the main-index-first background pass.
The compact count APIs were released in the single 0.90.0 #359/#576/#581 cache revision.
The additive query-total result changes no saved-fact interpretation or cache contract.

`ChunkseeIndex.RegionIndex` retains compact typed contributions; `DimensionIndex` owns replacement,
failed-read retention, selected deletion and complete cross-region aggregates. Its public
regionsToRead method supplies the read set for both the client scheduler and updating. The first
pass always covers all available regions; a completed empty/failed pass is distinct from never-read.
A broad pass removes
all unavailable regions; a partial pass preserves unselected contributions. Replacements must match
the dimension, selected/available coordinates, explicit cave-membership set. Empty successful
reads clear old values; an omitted available replacement retains them. Region traversal is X then Z;
native marker sort/presentation remains a client concern. Portal and biome joins happen after all
retained contributions are combined. Heightmaps and inhabited-time grids are not retained.
Every saved mob with a supported map location is retained, including ordinary unnamed/unowned
and custom types. These are in-memory values, with no persistence or file/task owner.

`CreatureEntry` owns the villager > owned pet > named > ordinary mob category precedence, stable
UUID/fallback identity and checked location eligibility through core BlockPosition.mapCoordinates
(floored X/Z fit Int32, supplied Y fits Int, unknown Y stays nil). Native map navigation and creature
eligibility share this public helper; it does not enforce the game world border.
The CLI uses `CreatureEntry.Group.group(for:)` for its existing special-category individual listings,
including unnamed villagers, without applying the map's location filter: text listings retain records
with unknown positions. Ordinary mobs remain in its per-type totals.
Player-carried shoulder pets remain a client projection; totals include every decoded creature.
The #276 extension adds the public `Group.mob` case and makes `Group.group(for:)` nonoptional;
both require a minor release and client adoption. Existing named/pet/villager raw values remain
unchanged for settings; the new raw value is mob. The creature search filter includes all groups;
pet/villager/trade filters keep their existing scope. Names, colors, symbols and
player-carried projections remain in the app. The additive region/dimension APIs are available in v0.46.0;
separate app adoption on fahlman/Chunksee#214 will remove its matching rules and retain cached native
marker projections for unchanged regions. Background-work scheduling and canceled-publication
guards remain app-owned. Tests use real synthetic scans, including cross-region joins and incremental
versus complete reads. No renderer, scan-ID, cave-membership or RegionFacts version change.

The palette-catalog extension adds `paletteBlockIDs` to RegionFacts, RegionIndex and DimensionIndex
for fahlman/Chunksee#365. Core collects the declared IDs from fully generated chunks' typed palettes
inside the existing section walk, regardless of the deposit-count filter. Unused palette entries
are included; this is a catalog, not evidence of occupancy. No second chunk decode or block traversal
is added. The regional set is retained compactly and dimension aggregation unions the retained
contributions, so successful replacement/deletion removes stale names while failed reads preserve
them. RegionFacts interpretation version 7 rejects older catalog-less archives. This additive API
is unreleased; app adoption follows its dependency release and keeps presentation/filter policy
outside the library.

`WorldIndex<Dimension>` owns the dimension-keyed world snapshot and its typed Placed/all enumeration.
The generic payload lets clients keep native projections with their shared facts, without a second
world catalog or UI imports here. Matching values in different dimensions remain separate records;
member order is preserved and dimension order is unspecified. Dictionary value semantics retain
earlier snapshots when a later one replaces a dimension. The app's reader catalog, background tasks,
cancellation and publication stay app-owned. This additive API is available in v0.47.0; app adoption and
remaining typed search-result work are tracked on fahlman/Chunksee#214.

`ItemTotals<Key>` owns matching-stack quantities, using the core ItemStack.allItems traversal for
nested contents. The caller supplies its predicate and grouping identity; searchable fields,
localized labels, ordering and output remain client-owned. CLI find uses its existing custom-name
or saved-ID key; StoredItemTotal uses saved IDs and keeps outer-container counts. A matching
zero-count stack remains a result. This additive API is available in v0.47.0; app adoption follows the
release on fahlman/Chunksee#214. No reader, inventory selection or cache meaning changes.

SearchSelection owns inventory-plus-saved-equipment inputs, saved book/sign search fields and
creature-filter membership. The CLI consumes PlayerInfo.searchableInventory, BookContent.searchText
and Sign.searchLines from this module. Saved whitespace and line boundaries remain significant.
The old WorldIndex.richestDeposits, DimensionIndex.ChunkDeposit/blocks and RegionIndex.blocks
APIs are removed in the unreleased cache revision; BlockCountIndex owns nearest selection.

`BiomeSampler` owns 26.3's seed-derived nearest biome-cell selection for four-block palettes.
It hashes the raw world seed once with Apple's CryptoKit SHA-256 and uses the game's wrapped
integer mixing, signed coordinate conversion and corner tie order. `cellOrigin(at:)` returns
the chosen cell's block origin, which can lie in a neighboring chunk/section. Out-of-Int32 input
is unavailable; the output is not narrowed, so extreme valid source coordinates cannot alias
another cell. `cellOrigin(at:in:)` applies the verified 26.3 source-chunk Y clamp using the
existing validated DimensionType's build limits, independently of logical height. It does not
read files, fill missing data, blend colors or change per-block palette semantics. Ordinary Chunk.biome remains a direct saved-cell
lookup. The additive API is unreleased for fahlman/Chunksee#361; app neighbor-data integration
follows a reviewed release. No serialized facts or RegionFacts interpretation change.

`Chunk.biomeSnapshot` projects an immutable ChunkBiomeSnapshot retaining only section Y values
and biome palettes. It does not keep the raw chunk, blocks or light arrays. Full Chunk/ChunkSection
and this view share one section lookup and cell/per-block addressing rule, preserving missing,
sparse, duplicate-height and invalid palette-reference behavior. Layout availability follows
the existing decoder, including uniform palettes' indistinguishable resolution. It performs
no I/O, nearest-cell selection, height clamping or color blending. This additive API is unreleased
for fahlman/Chunksee#361 so the app can reuse decoded neighbor biomes without retaining whole
chunks or decoding them twice. No stored facts or RegionFacts interpretation change.

The unreleased #128 `Chunk.keysNotNeededForBiomes` profile extends the terrain skip set with

Cell/per-block lookup and missing-data rules stay shared. As an explicit partial read, it does

bounded real-renderer comparison remain separate prerequisites to a performance claim.

The #314 ownership change added no supported format or numeric conversion. The #316 field-codec

Typed terrain facts expose the explicitly requested used-biome membership, a middle-column
biome sample. Block counting has its own terrain-only pass. The compact projection does not retain

The revision in `RegionFacts.interpretationVersion` must increase whenever a fact reader changes
meaning. Its typed `InterpretationVersion` also includes the release tool's generated-fact digest
and `Chunk.interpretationVersion`, so terrain changes invalidate dependent scans without a copied
counter. The complete value is stored in the archive and checked on decode. Old integer envelopes
are rejected. This #312 change intentionally replaces the public integer API and requires a minor

`Chunk`, `MonsterSpawnLight` and `GameAssets` publish the other interpretation contracts beside
their readers. They cover terrain/surface, saved light and its light check, and resource-derived
materials/colors (including saved-map colors). Light also includes the terrain dependency.
Each handwritten revision covers only its owner's interpretation. Generated digests come from
the single GameFacts entrypoint, whose explicit per-output domain coverage fails for an
unclassified new production file. Proof/provenance changes do not retire caches; changes to
covered production output do. Exact source bytes are hashed, so formatting can conservatively
retire a cache too. No release number, runtime UUID or randomized hash is an identity.
Consumers retain whole interpretation values plus their actual inputs. `RegionScanOptions`, `MonsterSpawnLight`,
`BiomeDefinition` and `MapItem` supply Hashable and Encodable conformances for whole-value keys;
they do not gain a new Decodable contract. `InterpretationKey.identity(of:)` is the single owner
of persisted SHA-256 identities and canonical binary property-list encoding. It explicitly sorts
keyed entries into ordered arrays and tags scalar values, independently of the writer's dictionary order.
Consumers call it once per immutable catalog publication and never configure their own encoder.
RegionScanOptions sorts its biome and structure-piece ID sets when encoding; nil and empty filters remain distinct.
Enchantment definitions are resolved from typed health inputs after reading, so they no longer
participate in the region scan or its persisted identity.
Region and count archives explicitly sort their palette/coverage ID sets.
Custom Encodable inputs define their own unordered collection encoding; ordered arrays stay ordered.
The canonical property-list tree encloses top-level scalars and distinguishes nil, text, booleans
and numbers. Corresponding Float/Double non-finite inputs agree; all NaN payloads normalize, and
ordered arrays retain their order. This new encoding retires previous JSON-based identities once.
Encoding errors throw instead of sharing a fallback identity. InterpretationOutputTests ties fixed
terrain, light, region-archive and resolved-asset output digests to each complete frozen contract,
including its owning reader revision and generated/dependent identities. Changed covered output
fails until a new reviewed contract/baseline is recorded; retain previous entries and never replace
an old contract's digest. Generated/dependent changes need no copied reader-counter bump.
Reader and generated-source identity checks cover invalidation and reuse, but unexercised
decoder paths still require independent review of the version contract.
InterpretationSourceTests also requires a reviewed source snapshot for the complete region-facts
contract. It fingerprints nonhidden files in the core-library and CZlib source roots plus Package.swift,
so a changed reader, added file or changed dependency declaration cannot rely only on fixtures
that happen not to exercise it. This is deliberately conservative: unrelated core edits also
request review. Hidden Finder/editor files are skipped because they are not package sources.
It changes no runtime cache identity and does not decide whether meaning changed.
Retain earlier source snapshots, and add a reviewed entry after a contract revision changes too.
A new snapshot may keep the same contract only when independent
review establishes unchanged interpretation; a meaning change still requires the owning revision
and the existing output-baseline review. Tests, documentation and provenance outside those source
roots do not affect the fingerprint. This first source-review gate covers region facts; it does
not replace the terrain, light or asset contracts or their fixed-output tests.
The #320 numeric-output fixtures also bind the captured SavedNumericSample inputs to those
contracts. Terrain covers coordinates, section/surface/biome access, saved times and light
validity; light covers both spawn-light rules through all four selective-read profiles; region
output comes from a real scan followed by archive decoding. Missing/nonnumeric fields, root/Level
precedence, and inhabited time beside malformed or unsupported terrain remain in these fixed
inputs. The original ordinary-output fixtures and their baselines are retained. These new
fixtures cover the declared cached chunk primitive families from #316, not every possible saved
field or the uncached player projections. Their baseline meanings come from captured game
results and the already-declared fixture contracts, never from recomputing numeric conversions
in another reader. Extending the input matrix is a new fixture baseline, not a reason to replace
an old contract's output digest.
The versioned envelope is the new Codable boundary, with options and dimension/region identity;
consumers also key all three file fingerprints and their own transform version. Older model
conformances remain source-compatible until separately migrated. The new API is available in
v0.30.0; Chunksee's pin and app adoption are separate work.

The unreleased #316 chunk-field correction uses the following declared readers in
`SerializableChunkData.parse`. Its `CompoundTag` numeric getters accept all six numeric tags;
they do not use the `Codec`/`NbtOps` boxed-number conversions. `NBTNumber` owns both families.

| Saved field | Game reader | Saved-data result |
|---|---|---|
| `xPos`, `zPos` | `CompoundTag.getIntOr` | Signed 32-bit conversion, widened to public `Int`; missing/nonnumeric required coordinates still fail |
| Section `Y` | `CompoundTag.getByteOr` | Signed byte conversion, widened to the section index; missing/nonnumeric section identity still fails |
| `LastUpdate`, `InhabitedTime` | `CompoundTag.getLongOr` | Signed 64-bit conversion; missing/nonnumeric saved metadata stays optional |
| `isLightOn` | `CompoundTag.getBooleanOr` | Converted byte differs from zero; missing/nonnumeric/skipped flags remain false |

Floating int/byte reads floor before JVM saturation and narrowing. Long reads truncate Float
but floor Double; NaN converts to zero, and out-of-range floating values saturate before any
byte narrowing. Integral long reads remain exact. This does not substitute the game's zero
fallback for missing saved coordinates or time metadata. `SavedChunkFields` retains its
root/Level fallback, independent inhabited-time reads survive bad terrain, and normalized
terrain retains its established Level merge precedence. Raw NBT and existing `javaInt`/`javaFloat`
codec meanings stay unchanged. DataVersion/yPos, older layout fixers' own field reads, and other
field families remain separate audit work, not evidence for blanket accessor replacement.

The field declarations and conversions are backed by retained official bytecode and 190
saved named-root inputs through real `NbtIo`, `CompoundTag`, `TagValueInput` and `NbtOps` readers
on #316. `SavedNumericSample` preserves all 180 numeric outcomes with source/input/result
hashes; public chunk, light, column and combined-region tests consume them. Missing/nonnumeric
cases, wrapped precedence and selective-read policy have separate coverage. Terrain revision 2
invalidates coordinates/sections/light validity; region-facts revision 30 covers its independent
inhabited-time interpretation. Light inherits the changed terrain identity without a copied
revision bump. Generated facts and the asset contract do not change. Required build/tests,
paired copied-world timing and independent review remain the publication gates for this slice.

## Releases

Ryan approved this process on 2026-10-09.

- A release is an annotated semantic-version tag on a commit that has been reviewed and merged
  to `main`:

  ```sh
  git tag -a vX.Y.Z -m '<summary>'
  git push origin vX.Y.Z
  ```

- Every tag needs Ryan's approval. Approval to merge is not approval to release.
- Before 1.0, the version number shows what changed:
  - Additive public API is a minor bump.
  - A breaking change is also a minor bump, but it must be named in the tag message. A breaking
    change includes adding a public enum case, because that breaks a downstream exhaustive
    `switch`.
  - Fixes that don't change the public API are a patch bump.
- Before tagging, run the required checks on the exact commit being tagged.
- Record the tag, its commit and the checks in the release's issue.
- Release order: tag ChunkseeKit first, then bump the Chunksee app's pin.
- The first release is `v0.1.0`, made after fahlman/ChunkseeKit#2 merges.
